# Глоссарий ядра: саммари и спека

Записи ведутся по одному шаблону: **определение** в одно предложение, **где в коде**,
**зачем** (какое свойство системы это обеспечивает), таблица **законов** и раздел
**не гарантируется**.

Два правила к шаблону:

- Идентификаторы законов — латиницей (`M1`, `C1`): по ним ищут в коде и в именах тестов.
- Колонка «Тест» обязательна. Закон без теста — намерение, а не гарантия; пока теста нет,
  в колонке стоит `нет`, и это видимый долг.

---

## Саммари (`S`, для текста — `TextSummary`)

**Определение.** Свёртка значения в величину, которую можно складывать: из саммари двух
соседних кусков получается саммари их склейки, не заглядывая в сами куски.

**Где в коде.** [`types.ts`](../../src/features/editor/types.ts) — параметр типа `S`;
для текста конкретизирован как `TextSummary`.

**Зачем.** Складываемость и есть причина, по которой навигация по дереву стоит `O(log n)`:
на спуске достаточно саммари ребёнка, разворачивать поддерево не нужно. Внутренний узел
хранит свёртку саммарей своих детей, поэтому при правке пересчитывается только изменённый
путь, а не всё дерево.

Поля `TextSummary` описаны в [`types.ts`](../../src/features/editor/types.ts). Два требуют
внимания: `linesCount` — это количество переводов строки, а не строк (у текста без `\n`
оно равно нулю), а `longestRow` при нескольких строках одинаковой длины указывает на первую —
см. «не гарантируется».

## Спека (`TreeSpec<T, S>`)

**Определение.** Набор операций, задающий, как значения типа `T` складываются, режутся и
сворачиваются в саммари типа `S`.

**Где в коде.** [`types.ts`](../../src/features/editor/types.ts) — тип;
[`spec.ts`](../../src/features/editor/spec.ts) — реализация для текста (`sumTreeSpec`).

**Зачем.** Спека — единственное место, которое знает, что лежит внутри листа. Дерево
(`build`, `merge`, `slice`, `seek`) оперирует только высотами и саммари, поэтому одно и то же
дерево работает над любым `T`, для которого спека написана.

```ts
export type TreeSpec<T, S> = {
  default: () => S;
  summary: (value: T) => S;
  combine: (leftSummary: S, rightSummary: S) => S;

  size: (value: T) => number;
  concat: (a: T, b: T) => T;
  split: (value: T, at: number) => [T, T];
  maxSize: number;
}
```

Формально вся конструкция сводится к одной фразе: `(S, combine, default)` — моноид,
`(T, concat, empty)` — моноид, а `summary` — гомоморфизм между ними. Законы ниже — это она,
расписанная по пунктам.

### Законы: моноид

| # | Название | Формулировка | Тест |
|---|----------|--------------|------|
| M1 | Нейтральный элемент | `combine(s, default()) = combine(default(), s) = s` | [`spec.test.ts:23`](../../src/features/editor/spec.test.ts#L23) |
| M2 | Ассоциативность | `combine(combine(a, b), c) = combine(a, combine(b, c))` | [`spec.test.ts:28`](../../src/features/editor/spec.test.ts#L28) |
| M3 | Гомоморфизм | `summary(concat(a, b)) = combine(summary(a), summary(b))` | [`spec.test.ts:33`](../../src/features/editor/spec.test.ts#L33) |
| M4 | Пустое значение | `summary(empty) = default()` | [`spec.test.ts:41`](../../src/features/editor/spec.test.ts#L41) |

M3 — главный закон всей конструкции: он разрешает считать саммари склейки, не трогая сам
текст. Без него спуск по дереву пришлось бы делать обходом листьев.

### Законы: чанкинг

| # | Название | Формулировка | Тест |
|---|----------|--------------|------|
| C1 | Ассоциативность `concat` | `concat(concat(a, b), c) = concat(a, concat(b, c))` | нет |
| C2 | Аддитивность `size` | `size(concat(a, b)) = size(a) + size(b)` | нет |
| C3 | Обратимость разреза | `concat(...split(v, at)) = v` для любого `at` | нет |
| C4 | Края | `split(v, 0) = [empty, v]`, `split(v, size(v)) = [v, empty]` | нет |
| C5 | Точка реза | `abs(size(split(v, at)[0]) − clamp(at, 0, size(v))) ≤ 1` | нет |
| C6 | Границы чанка | при `size(v) > maxSize` и `at = ceil(size(v) / 2)` обе части лежат в `[minSize, maxSize]` | нет |

Ни один из C-законов пока не проверяется, и это главный долг документа: текущая реализация
`split` в [`spec.ts`](../../src/features/editor/spec.ts) возвращает два первых символа хвоста
вместо префикса и суффикса, то есть нарушает C3, C4 и C5 одновременно. C3 — первый кандидат
в тесты: он падает на текущем коде сразу.

Допуск `≤ 1` в C5 не небрежность: точка реза может сдвинуться на единицу, чтобы не разорвать
суррогатную пару. Допуск надо держать явным, иначе после починки `split` закон начнёт мешать.

C6 опирается на соотношение `maxSize = 2 · minSize`. Это не произвольный выбор: если
`size(v) > maxSize = 2 · minSize`, то каждая половина больше `minSize`, а так как
`size(v) ≤ 2 · maxSize`, каждая не больше `maxSize`. Обе границы держатся ровно на этом
соотношении, и при его изменении C6 перестаёт выполняться.

### Не гарантируется

- **`combine` не коммутативен.** Порядок аргументов значим — это левый и правый саммари.
  Записывать `combine(a, b) ≠ combine(b, a)` как закон нельзя: при `a = b` или когда обе
  части `default()`, равенство выполняется. Проверяемая форма — свидетель: существуют
  `a`, `b`, для которых результаты различаются.
- **Обратного элемента нет.** Это моноид, а не группа: «вычесть» саммари из свёртки нельзя,
  пересчёт идёт только сложением.
- **`S` неизменяем, `combine` чист.** Иначе разделяемые между узлами массивы
  `childSummaries` начнут алиаситься, и правка одного узла испортит соседние.
- **Конкретно у `sumTreeSpec`:** при нескольких строках одинаковой максимальной длины
  `longestRow` указывает на первую. Это выбор реализации, а не закон интерфейса.

### Открытые вопросы

1. **`empty: () => T`** в `TreeSpec` нет, хотя нейтральный элемент `T` нужен для C4 и для
   того, чтобы M3 был сформулирован до конца. Без него `Leaf.empty` вынужден делать
   `String(this._value).length === 0`, что для произвольного `T` бессмысленно.
2. **`minSize`** живёт в [`constants.ts`](../../src/features/editor/constants.ts) как
   `CHUNK_MIN`, отдельно от `spec.maxSize`. Из-за этого расхождения `joinLeaves` сравнивает
   с константой модуля, а не со спекой. Либо поле рядом с `maxSize`, либо явно выводимое
   `maxSize / 2` — но зафиксированное.
3. **JSDoc у `linesCount`** в [`types.ts`](../../src/features/editor/types.ts) описывает поле
   неверно («a point representing the number of lines and the length of the last line»),
   это остаток от прежней структуры саммари.
